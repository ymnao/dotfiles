# Shell スクリプト規約

**適用範囲に `SKILL.md` を含める。** skill の手順書は拡張子こそ `.md` だが、
中のコマンドは agent がそのまま実行するので、実体は shell スクリプトと同じ
危険を持つ (PR #331 の実例は「受理パターンの広さ」項に置いた)。**ロードは
適用の必要条件であって十分条件ではない** — 同項の適用漏れは `*.sh` 側でも
起きている (issue #284 は 3 周連続)。

- **bash 3.2 互換で書く**(macOS 標準)。連想配列(`declare -A`)、
  `${var,,}` / `${var^^}`、`readarray` は使わない。小文字化は
  `tr '[:upper:]' '[:lower:]'` を使う
- **BSD / GNU 両対応で書く**。`sed -i` は使わない(引数仕様が非互換)。
  `grep -P` は使わない(`-E` を使う)。`date -d` / `stat -c` 等の
  GNU 拡張を避ける
- 新規スクリプトは `set -euo pipefail` から始める。exit code を自分で
  扱うスクリプトは `set -uo pipefail` にして理由をコメントに書く
- 変数展開は常に quote する(`"$var"`)。word splitting に依存しない
- **日本語などの多バイト文字が直後に続く変数展開は必ず `${VAR}` とブレースで
  囲む**。bash 3.2 + UTF-8 ロケールでは多バイト文字の一部バイトが変数名に
  取り込まれ、未定義変数として誤パースされる(`set -u` だと即死)
- **ロケール依存のあるテスト・スクリプトはロケールを明示 pin し、理由コメントを
  書く**(ambient ロケール頼みにしない)。バイト同一性を検査する箇所(BSD awk
  の `==`、日本語文字列比較、sort 順依存等)は `LC_ALL=C` 固定、逆に「UTF-8
  ロケール下での挙動」を回帰検査したい箇所は `LC_ALL=en_US.UTF-8` 等を明示
  pin する。pin の粒度は次のどちらでもよい:
  (a) shebang 直下で `export LC_ALL=...` — スクリプト全体が同じロケールに
      依存する場合 (実例: `tests/agents-md-sync/run-agents-md-sync-check.sh`)
  (b) ケース単位で `LC_ALL=... command args` 形式で行スコープ pin — 特定
      ケースだけ非デフォルトロケールを検査したい場合 (実例:
      `tests/verify-ci/run-verify-ci-tests.sh` の `stderr-defer-policy-utf8`
      ケース = `LC_ALL=en_US.UTF-8`)。
  CI は `make test` を LC_ALL matrix で 3 ロケール並列に回すため、pin 忘れは
  多くの場合 matrix job のどれかで fail する(issue #181)。ただし matrix の
  自動検出は「テストのアサーションが結果差を assert する」ケースに限る:
  silent に間違った値を返してもテスト側が拾わないパス、あるいは matrix に
  含まれない特殊ロケール(`ja_JP.SJIS` 等)固有の依存は matrix でも素通しに
  なるため、規約としての pin は依然必要
- 変更後は shellcheck(`-S warning`)を通す。警告はコードを直して解消し、
  disable コメントは追加しない
- **テストの floor / guard は「守る対象」から導出しない**。「必須ケースが
  実行されたか」を検査する下限値やガードは、検査対象そのもの(ケース一覧の
  配列長、対象ツールの数等)から計算すると、対象が減ったときに下限も一緒に
  下がって検出が無効化される。期待値は独立した定数として持ち、対象と食い違ったら
  fail させる。あわせて 2 点:
  - 数えるのは pass 数ではなく **実行数**(pass + fail)。pass を見ると
    「実行されたが FAIL した」を「実行されていない」と誤って報告する
  - **任意ケース(host 条件で skip されるもの)の分は差し引く**。含めると、
    任意ケースが走る環境では必須ケースの欠落が埋められて素通りする
  実例: `tests/fish-version-managers/run-fish-version-managers-tests.sh` の
  `EXPECTED_TOOLS` / `MANDATORY_PER_TOOL` / `optional_ran`(PR #224。当初は
  `${#TOOLS[@]} * 5` と対象から導出しており、上記 3 経路すべてで素通りしていた)
- **fail-closed にしたら、次は「受理パターンの広さ」を検査する**。「解析できない
  ものは fail にする」設計は*拒否側の既定*を安全にするだけで、*受理側*の口が
  広すぎれば素通りは残る。危険な入力が「解析できなかった」ではなく
  「**解析できてしまった**」経路で通るため、fail-closed にした安心感が
  そのまま盲点になる。受理パターンを書いたら、**それにマッチしてしまう危険な
  入力**を自分で構成して試す(マッチしない入力を試すだけでは足りない)。
  実例: issue #213 の対応で 2 周連続で踏んだ。1 周目は「command から repo 参照の
  断片を抽出して照合」する形で、断片が 1 つ取れると同じ command 内の他の参照が
  捨てられた(`bash "$A" && bash /tmp/evil.sh` の後半)。2 周目は受理パターン
  `^(bash|sh|...) "?([^"]+)"?$` の `[^"]+` が空白を含むため、クォート無しで
  書くと後続コマンドごと 1 個のパスとして吸い込まれ、前方一致で「監視対象内」と
  判定された。いずれも「未知の形は fail」という規約自体は満たしていた。
  実例: PR #331。ブランチ名の安全な文字集合を検査する `awk` を SKILL.md に
  書いたが、**判定器の exit code を敵対入力で測っていなかった**。`awk` の
  main rule の `exit` は END を実行し、END 側の `exit <expr>` が status を
  上書きするため (`printf 'x\n' | awk '{exit 7} END{exit 3}'` は 3)、
  `... {exit 1} END{exit NR!=1}` は 1 行入力なら何でも exit 0 になり
  `foo$(id);x` を受理していた。受理パターンを書いたら、**パターンだけでなく
  判定器の exit code も主張の一部**として両方向で測る
  (`tests/branch-name-validator/` がこの挙動を pin している)
- **他実装が正規化した後の値を判定するなら、その正規化を一次情報で確認して
  再現する**。前項が「自分が書いた受理パターンの口が広すぎないか」なのに対し、
  こちらは**同じ文字列を読む 2 つの実装のズレ**の話。判定側が正しくても、
  *相手が何を同一視するか*を写し取っていなければ、ズレの分がそのまま
  バイパスになる。しかも**自分のコードだけを読んでも見つからない** —
  ガードのロジックは意図どおり動いており、間違っているのは「相手はこう読む」
  という**書いていない前提**の方だから。
  手順そのものは後段の「『確認できない』を検査を緩める根拠に使わない」項と同じ
  (一次情報で確認する / 確認できない分は厳しい側に倒す)。**この項に固有なのは
  2 点**: 確認する対象が自分の判定ではなく**相手の正規化**であること、
  厳しい側 = 相手より広く正規化する (過剰 block = fail-closed) なので、
  **広げすぎを検出する過剰側のラチェットも同時に置く**こと — 広い側に倒した
  ことだけを pin すると、集合を広げすぎた退行が誰にも見えなくなる。
  実例: issue #308。`guard-codex-dir.sh` の apply_patch ヘッダー抽出は
  `$0` をそのまま使っていたが、codex のパーサは行末 CR を落とし Rust の
  `str::trim`(Unicode の White_Space 全部)で前後を trim してから path を
  取る(2026-08-10 に `codex-rs/apply-patch/src/streaming_parser.rs` で確認)。
  パーサは実 path へ書くのに完全一致判定だけが外れるため、**対照付きの実測で
  LF 以外の 11 形(行末 CR / スペース / タブ / VT / FF / U+00A0 / U+3000 と
  行頭スペース / タブ / U+00A0)がすべて素通りしていた**。issue が挙げていた
  CRLF はその 1 事例にすぎず、着手時に相手の実装を読むまでスコープを
  読み違えていた。prefix 一致で判定していた層は `/*` が CR を吸うため無傷で、
  露出したのは完全一致の 1 経路だけ — **同じ入力でも判定の形によって
  当たり外れが変わる**ので、ズレの影響範囲は判定ごとに見る
- **hook 自身を調べるとき、guard に阻まれても回避形を組み立てない**。この repo の
  hook は**自分が打つ Bash コマンド**も検査するので、hook をレビュー・調査すると
  テストに使いたい入力がそのまま自分の guard に引っ掛かる。ここで文字列を分割・
  連結して通すと、目的が正当でも**やっていることは防御機構の回避**で、しかも
  「回避できた」という観測だけが残って**その経路が塞がっていないことの証拠に
  なってしまう**。測りたい入力は `tests/run-hook-tests.sh` 経由か、payload を
  ファイルに書いてから hook に流す。それでも測れないなら回避せず
  「この形は測れなかった」と報告する — **未測定の報告は無害だが、回避は防御
  そのものを壊す**。
  実例: 2026-08-10、`guard-codex-dir.sh` の変更 (issue #308) をレビューさせた
  code-reviewer サブエージェントが、`.codex` を含むテスト payload を分割連結で
  組み立てて guard を回避し、security warning が出た。2 周目に回避しないよう
  明示指示したら、テストランナー経由に切り替えて同じ検証ができていた。
  **`agents/hooks/` を触る PR では毎回この状況になる**ので、レビューを依頼する
  側は指示に含める (`claude/agents/code-reviewer.md` からこの項を指している)
- **判定の前処理で文字列を「削除」しない。検出と削除を分ける**。「受理パターンの
  広さ」の項が*検査手順*の話なのに対し、これは**失敗の向きを決める構造**の話。危険判定の前に文字列を
  削除・置換して正規化すると、境界の見誤りが「**危険な形を無害な形に化かす**」=
  fail-open として出る。検出だけを行い元テキストを保つ設計なら、同じ見誤りは
  「余分に検出する」= fail-closed で済む。**同じ間違いでも、削除する設計だけが
  防御を消す側に倒れる。**
  あわせて、**境界文字集合は仕様から取る**。「パス文字でない」「空白」のような
  直感的な補集合で書くと、実際の word 区切り(POSIX shell メタ文字
  `| & ; ( ) < > space tab newline`)とずれる。特に `[[:space:]]` は VT(0x0B) /
  FF(0x0C) / CR(0x0D) を含むが、**bash はこの 3 文字を word 区切りにしない**
  (ファイル名の一部になる)。空白を区切りとして使うなら `[[:blank:]]`(space + tab)。
  実例: issue #284 で fd リダイレクトのマスクから **3 周連続で fail-open** が出た。
  (1) 右境界が無く `>&1/../<保護対象>/evil` の `>&1` を fd 複製と誤認して消し、
  本物の書き込みが判定から消えた。(2) 境界を `[^A-Za-z0-9_./-]`(= パス文字でない)
  で定義したため、ファイル名に使える 13 記号(`! # % + , : = ? @ [ ] ^ ~`)が
  区切りに見えて同じ穴が開いた(実測で bash は 13/13 で書き込み成立、hook は
  13/13 allow)。(3) 空白側を `[[:space:]]` にしたため VT/FF/CR が素通りした。
  3 回とも「受理パターンの広さ」項の「マッチしてしまう危険な入力を自分で
  構成する」の適用漏れで、
  マスクが**既に検出済みのリダイレクトを消す**という共通の経路を通っていた。
  構造の是非自体は issue #289 で別途扱う
- **pin を足したら「何を測っているか」を実測で確かめる**。守りたい状態を測れて
  いないまま緑になる pin は、あるだけで「検査済み」の錯覚を作る。典型的な外し方は
  2 つ: (a) `2>&1` で捕った出力を **stdout の形式**として検査する(stderr の 1 行が
  混じるだけで誤検知にも見逃しにも倒れる)、(b) コマンド置換が先頭・末尾の改行を
  落とすことに気付かず「1 文字目」を取る(先頭が改行だと空文字になり、比較が
  全部通る)。**pin の効き目は、守りたい状態を実際に作る mutation で確認する**
  — マッチしない入力を試すだけでは足りない(fail-closed の受理パターン検査と
  同じ構図)。可能なら 1 文字ではなく**行全文**を pin する。
  実例: issue #215 で「hook の stdout が `{` / `[` で始まらないこと」の pin を
  足したが、上記 (a)(b) の両方を踏んでいた(先頭に空行 + `{` を出す mutant が
  スイート全 pass のまま通った)。先頭行の全文 pin に直して塞いだ。
  (c) **1 行目だけを見て「クリーンに落ちた」と判定する** — エラーメッセージを
  出してから throw / abort する実装は 1 行目が正しいまま stack trace を続けて
  出すので、素通りする。見るのは「あるべき行があること」だけでなく
  **「あってはならない行が無いこと」**(stack frame `^[[:space:]]+at ` 等)。
  実例: issue #264 の renderer で、検証失敗を `html-brief: <理由>` で落とす
  仕様を pin したつもりが、`process.exit(1)` を `throw` に置換した mutant が
  41/41 pass で通った(`fail()` は stderr に書いてから exit するため)。
  frame の有無を見る判定に直したら同じ mutant が 19 件 fail に転んだ
- **repo 全体を走査する使い捨てスクリプトも、まず「既知の陽性を 1 件仕込んで
  検出できること」を確かめる**。上の 2 項が repo に残す pin の話なのに対し、これは
  **その場限りの調査スクリプト**の話。「N 件中 0 件」という出力は、本当に 0 件
  なのか走査が空振りしたのかを区別しない。0 件は最も安心できる結果なので、
  そのまま「対応漏れなし」と報告してしまう。抽出が期待どおりかを 1 件だけ目視し、
  既知の陽性が拾えることを確認してから全体を回すこと。
  実例: issue #267 の対応で、repo 内の ` ```bash ` ブロックを hook に流して誤ブロックを
  探す走査を書き、**2 回続けて「0 件」と誤報告した**。1 回目は awk の buffer に
  実改行を入れたため TSV の 1 行目しか読めず全ブロックが 1 行に化けていた。
  2 回目は行頭の fence しか拾わず、リスト内にインデントされたブロック
  (`claude/skills/resolve/SKILL.md`) を落としていた — そこが実際に壊れており、
  レビュアーが独立に走査して見つけた
- **環境の前提を assert するときは「守りたい挙動そのもの」を測る**。版数・パス・
  オプション対応の有無といった**プロキシで実装の同一性を判定すると、上流が
  変わった瞬間に静かに陳腐化する**。「pin の効き目を mutation で確かめる」項が
  *測り方*の外し方なのに対し、こちらは
  *判定基準の選び方*の問題で、mutation で確かめても「基準そのものが的外れ」は
  検出できない。プロキシ判定は診断用のログ出力に格下げし、判定は挙動で行う。
  挙動 probe が通らなくなったときに fail することは仕様 — 前提が消えたことを
  green で隠さないため。
  実例: issue #244 で macOS CI の awk 判定を「`--version` を受理する = GNU awk」
  というヒューリスティクスで書いていたが、one-true-awk が `--version` を受理する
  ようになったことで false positive に転び、**環境検証で落ちて本体テストが一度も
  走らないまま週次で赤を出し続けていた**。「en_US.UTF-8 で日本語 2 文字列が `==` で
  誤 equal になるか」という挙動 probe (= その CI が踏みたいバグそのもの) に
  置き換えて塞いだ
- **「確認できない」を検査を緩める根拠に使わない**。上の 2 項が*測り方*と
  *判定基準の選び方*の話なのに対し、これは**そもそも測らなかった**ときの話。
  「実装非公開」「ソースが読めない」と書いた直後に挙動を断定し、その断定を
  根拠に検査を緩めると、**誤りが「検証済みでない」ではなく「検証しなくてよい」
  という形で構造に埋まる**。手順は 2 つ:
  (a) **断定を書く前に確認手段を一度は探す** — 非公開でも配布バイナリの
      `strings`、公式 docs、実際に発火させた観測など、たいてい何かはある
  (b) **それでも確認できないなら、緩い側ではなく厳しい側に倒す** — 検査は
      通しうる最も厳格な形 (全文 pin 等) にしておく。前提が外れていたときの
      被害が「テストだけが通る」ではなく「テストが落ちる」側に出る
  実例: `docs/ai-operations.md` §10 が「Claude Code 側は実装非公開のため
  同じようには確認できない」と書いたうえで「Claude Code の matcher は
  regex 一本槍」と断定し、**それを根拠に Claude 側のテストだけ bash の `=~`
  (部分一致) による緩い検査を許していた**。実際にはバイナリを読めば確認でき、
  Claude Code も codex と同じ 3 分岐 (match-all / exact / regex) で、
  `startup|resume|clear` は exact 一致側だった。つまり `tartup|esume|lear` の
  ような綴り違いが全 assert を通るのに一度も発火しない状態で、これは同節が
  codex 固有の危険として明記していた穴と同型。同じ前提は
  `tests/integrity/verify-guard-codex-wiring.sh` にも残っており、そちらは
  遮断層 (`guard-codex-dir`) の配線検査だった (issue #245 step 1 のレビューで発覚)
- **codex に配線する hook の stdout は `{` / `[` で始めない**。codex は hook の
  stdout がその 2 文字で始まると JSON 出力とみなし、パースに失敗した時点で run を
  `Failed` にして**本文を model の context に入れない**(実測根拠は
  docs/ai-operations.md §10)。Claude Code 側は素通しなので、**片方の harness でだけ
  静かに壊れる**形になる。防御は 2 層で、**どちらも必要**(issue #240):
  - **静的**: `scripts/lint-hook-stdout.sh` が `agents/hooks/` `claude/hooks/`
    `codex/hooks/` を横断検査し、`make test` を fail させる。拾えるのは
    **リテラルとして書かれた出力**だけ
  - **実行時**: 変数展開経由の出力は静的には見えないので、hook ごとに
    **stdout 単独 (`2>&1` で取らない) で先頭行を全文 pin** する
    (実例: `tests/session-compact/` `tests/hooks-integrity/`)。
    **新しく stdout を出す hook を codex に配線するときは pin を足す** —
    自動では強制されない
  linter が取りこぼす形を見つけたら、`tests/lint-hook-stdout/` に `form_case` で
  回帰ケースを足してから直す。取りこぼしの既知の形は linter 冒頭コメントにある
- **「全部入り」を名乗る fixture は、対象が増えた瞬間に黙って古くなる**。
  「全 X を含む入力」「全 Y を通す」と書いた fixture は、X が増えたときに更新を
  強制する仕組みが無いと、**新しい X だけが一度も検査されない**状態になる。
  しかも fixture のコメントは「全部入り」と主張し続けるので、読んだ人は
  覆われていると思う。前 2 項が*下限値*と*集合の共有*の話なのに対し、これは
  **同じ問いに答える 2 箇所 (fixture と対象) が乖離する**話で、drift のように
  片方の更新忘れが目に見える形では壊れない — 増えた側だけが無検査になる。
  **fixture の要素数と対象側の実数が一致することを機械で測る**こと
  (どちらも独立した定数にはできないが、乖離の検出はこれで足りる)。
  実例: issue #264 で `tests/html-brief` の `ALL_TYPES` が 5 型のまま
  section 型を 12 に増やし、追加した 7 型の出力が subresource 検査にも
  href 検査にも一度も通っていなかった。レビュアーが `tiles` に `href` を
  出す mutant を当て、**72/72 pass で素通りする**ことを示すまで気付けなかった
- **集合を共有してよいのは「問い」が同じときだけ**。「同じ意味の集合を 2 箇所に
  書くと片方だけ更新されて drift する」は正しいが、その規約に従いすぎると
  **答えが割れる 2 つの問いを 1 つのパターンに畳む**という逆向きの失敗をする。
  drift は「更新を忘れる」形で*目に見えて*壊れるのに対し、こちらは
  **共有した瞬間から静かに間違っている**ので、テストを足しても
  「そもそもそのケースを書こうと思わない」形で残る。
  判定は「このパターンを使う 2 箇所は、同じ問いに答えているか」を 1 文で
  書けるかどうかで行う。書けないなら分けて、両方に触れるときの判断基準を
  コメントに残す(集合を 1 つにするのではなく、*基準*を 1 箇所に書く)。
  実例: issue #255 で `classify-risk.sh` の「レビュー床の除外」を
  「content check の除外」(`NOT_EXECUTABLE_DOC_PATTERN`) の再利用で書いた。
  前者は「この文書はエージェントが指示として読むか」、後者は「この行を
  grep して実行構文を探す価値があるか」で、`docs/ai-operations.md`
  (散文だが `agents/AGENTS.md` から参照される運用指示) は答えが割れる。
  結果、その文書の変更が tier=low = **無レビューで merge** できる状態を
  作った。自分では drift 防止の模範例のつもりで書いており、
  codex-review security が具体的なファイル名を挙げるまで気付けなかった
- **パス集合を入力にするルールを足したら、必ず rename を測る**。
  `git diff --name-only` は rename の**宛先しか返さない**ため、元パスに
  依存する判定は「ファイルを別名に動かす」だけで外れる。削除
  (`--diff-filter=D`)を塞いだことで安心しやすいが、rename は削除の
  仲間ではなく**別経路**で、`git config diff.renames` の状態にも左右される。
  元パスも見たいときは床/ゲート側の入力だけ `--no-renames` で取り直す
  (rename が delete + add に分解される)。既存の判定と入力を共有すると
  そちらの意味論まで変わるので、共有せず取り直すこと。
  実例: issue #255 の medium 床は、指示文書の**削除**を塞ぐ回帰ケースまで
  書いておきながら、`git mv claude/skills/foo/SKILL.md README.md` で
  同じ「指示文書が無くなる」変更が tier=low で通った。この repo は
  `check_deleted` の `--diff-filter=D` で同じ盲点を既に踏んでおり
  (`test-rename` ケースはそのために書かれている)、**2 回目**だった
- **mutation check は 1 回に 1 変数だけ変える**。複数変えた mutant が FAIL しても
  どの変数が検出されたのか特定できず、誤った因果をコメントに残す。
  実例: issue #218 の対応で `fish_add_path -g` を `--path -a` に変えた mutant
  (スコープと append 性の 2 変数) が FAIL したことから「`-g` が PATH 順序を
  決めている」と結論づけたが、`--path` 単体でも順序は変わらず、実際に順序を
  決めていたのは config.fish の実行順だった(`-g` の役割は universal 化の回避)
- **過去の実測値を、新しい fixture の閾値の根拠に流用しない**。issue や commit
  message に残った数字は**そのとき動いていたコード**の上で測られたもので、今の
  コードとは別物でありうる。特に危ないのが、退行を直した commit が**同時に
  別の高速化も入れている**形 — 退行だけを注入した mutant には高速化が残るので、
  当時の入力サイズでは差が閾値まで開かない。入力サイズを振って**今のコードで
  測り直す**こと。
  実例: issue #314 の pin で、この節の後段 (「毎回走るゲートに…」の項) が
  記録している #311 の実測値をそのまま fixture の長さにした。あの値は
  95b690d 以前の測定で、同 commit が入れた `_matches_codex` の fast path が
  無い。fast path のある現行コードに退行 (`${_tail%%/*}` の切り詰めを外す)
  だけを当てると 2.92s にしかならず、10s 閾値を跨がずに pass した。
  7215 字まで上げて 91.0s (正常 0.36s) で分離した
- **mutation を適用したら「実際に変わった行」を diff で確認する**。この repo は
  設計コメントが厚く、コード行と同じ字面がコメント側にも現れるため、
  `perl -pi` / `sed` の置換が**コメント行に当たって空振りする**。空振りに
  気付かないと「テストがこの経路を検出できなかった」という**偽陰性**の結論に
  なり、実在しないテストの穴を報告することになる。置換前後の `cmp` では
  不十分 — コメントが変わる分だけ差分は出るので「適用された」に見える。
  実例: issue #232 の対応中に 2 回踏んだ。`s/shasum -a 256 /shasum /` が
  コード行ではなく `# macOS は shasum -a 256 (coreutils 非前提)` に当たり、
  スイートが全 pass したため一度は「未検出」と報告しかけた(コード行を狙い
  直すと 4 件 FAIL で検出できていた)。
  **確認するのは「当たったか」だけでなく「当たりすぎていないか」も**。この repo は
  同型のブロックが複数箇所にあるため(抽出用の awk、祖先を遡る解決ループ等)、
  1 箇所を狙った置換が別の箇所にも当たる。**過剰適用は空振りより見つけにくい** —
  空振りはテストが赤くなるが、過剰適用は**別の理由でテストが緑になる**ことが
  ある。`git diff` で変更された箇所を**数える**こと。この項は mutation だけの
  話ではなく、本体を一括置換で編集するときも同じ。
  実例: issue #291 の対応で、候補レコードにタグを付ける置換が、意図した
  `extract_edit_paths_nul` に加えて既存の `extract_paths` 側の同型 awk にも
  当たった。タグが Bash token 側の候補集合へ漏れ、実在しないパスが cwd 配下に
  見えて**過剰 block** に倒れた。このとき「保護対象が先頭でない複数候補」の
  テストは**その過剰 block のおかげで緑**になっており、別の mutation
  (先頭候補だけ判定する)を当てるまで空振りに気付けなかった
- **mutation を戻すのに `git checkout <file>` を使わない**。前 2 項が mutation の
  *当て方*の話なのに対し、これは*戻し方*。mutation を当てるのは本編集の途中なので、
  ファイル単位で HEAD に戻すと**同居する未 commit の本編集も消える** — 失うのが
  「まだテストに掛けていない編集」なので気付く手掛かりが無い。戻すのは
  **当てたときと同じ置換の逆向き**で行い、`git diff` が適用前と一致することで
  確認する。本編集を先に commit してから当てれば、この衝突自体が起きない。
  実例: issue #288 (mutant を戻す `git checkout` で、同じファイルの未 commit の
  コメント書き換えと列挙追加を巻き添えにした)
- **毎回走るゲートに「suffix ごとに検査を回す」形を足したら、病的入力の実行時間を
  測る**。正しさの回帰テストは通ったまま、入力長に対して超線形に伸びる経路が入りうる
  — 内側の検査が文字列全体を再走査するなら、外側のループ回数との積で O(n²) 〜 O(n³)
  になる。ゲートが hook なら**全コマンドで毎回**払うコストなので、遅さはそのまま
  シェルの摩擦になり、harness 側が hook を打ち切る実装なら防御の回避にもなる。
  候補を足すループを書いたら、**切り詰めてよい位置 (= 先に検査済みの範囲) を 1 文で
  言えるか**を確認すること。
  実例: issue #311 で、レビュー指摘に応じて `=` の位置ごとに派生候補を取る形にした
  際、候補として残り全体を渡して `/` 分割をやり直していた。`a=/a=/…` の 1816 字で
  82.07s (main は 0.45s)。機能テストは全 pass のままで、2 周目のレビューまで
  気付けなかった。候補を最初の `/` までに切って 0.18s に戻した
- **コメントに書く「外部環境の事実」は、書く前に実測して測定日を添える**。
  runner イメージの pre-install 内容、ダウンロード先ドメイン、成果物サイズ、
  `bash` / `awk` の解決先、CLI オプションが実際に拾うエラー種別などは、
  もっともらしく書けてしまう上に**設計判断の根拠として引用される**ため、
  外れると判断ごと腐る。「〜なので依存は増えない」「〜MB なのでキャッシュ不要」
  のような**根拠つきの断定**を書くときは、その根拠を必ず 1 回測る
  (`curl -sI` の Location、`ls -l` のバイト数、runner-images の README、
  `man` の該当項)。測定日を添えるのは、後から読む人が「いつの事実か」を
  判断できるようにするため。
  実例: issue #196 の対応で 1 PR のうちに 4 件外した — release asset は
  `release-assets.githubusercontent.com` へリダイレクトされるのに「失敗
  ドメインは増えない」、tarball は 2.4MiB なのに「~1.5MB」、`bash <path>`
  起動では shebang が参照されないのに「shebang 側で決まる」、
  `--retry-connrefused` は ECONNREFUSED だけなのに「DNS 失敗も再試行される」。
  いずれもレビュアーが実測して覆した(2 周連続)。
  **ただし測定日を添えること自体は保証にならない** — 推論に日付を付けても
  形式だけは満たせてしまうので、「(YYYY-MM-DD 実測)」と書く行は
  **その 1 行が対応するツール実行結果を指せるか**を書いた直後に確かめること。
  とくに**否定形の断定**(「〜すると壊れる」「〜は効かない」)を設計判断の根拠に
  するときは、**対照付きで**測ってから書く(効かないことの観測は、
  「設定が読まれていない」でも同じ結果になるため、対照が無いと区別できない)。
  実例: issue #289 (PR #292) で 2 回。「`~/**/…` は `**` の 0 段マッチで
  `~/.codex/` を巻き込む」は対照付きで測ると逆(エントリは効いているのに
  `~/.codex/<file>` は書けた)、「末尾の `/**` が落ちた形は効かない」も
  測ると効いた。どちらも「(実測)」タグ付きで書いており、片方は
  **どの表記を出荷するかの選択理由そのもの**だった。
  なお**この項を lint で機械検出することはしない** — 「実測」ラベルの真偽は
  行の字面からは判定できず、`scripts/lint-locale-pin.sh` (issue #192) のような
  「pin の有無」を見る静的検査に相当するものが作れないため
- **測る対象が repo 自身なら、その数値をコメントの根拠にしない**。上の項が
  *測ったかどうか*の話なのに対し、これは**測定日を添えて実測しても決着しない**
  ケース。コーパスが repo 自身だと (a) その節を書き足す行為自体が数を動かし、
  (b) 走査方法の些細な差 — `git grep` は blob を見るので symlink 配下が
  当たらない、`git ls-files` + 追従読みだと当たる — で別の値になる。結果、
  レビューのたびに「どちらが正しいか」の往復だけが増える。書くなら
  **走査方法と自己参照性を明記し、絶対値ではなく同一時点で取った差分**
  (旧パターンと新パターンの増分など) を判断に使う。
  実例: issue #230 の対応で「旧 `eval ` にマッチするファイル数」が
  57 / 60 / 62 と 3 回とも違い、うち 2 回はレビュアーとの食い違いになった。
  同一時点の「4 経路 = 10 / 5 経路 = 10、増分 0」の側は毎回再現した
- **「こうすれば回避できる」と書いたら、その手順を一度は実際に通す**。上の 2 項が
  *事実の断定*をどう測るかの話なのに対し、これは**手順の実行可能性**の話で、
  外れ方が違う — 事実の誤りは読んだ人が別の事実に突き当たって気付けるが、
  回避手順の誤りは**手順どおりにやっても何も起きない**形で出るので、間違いだと
  気付く手掛かりが無い。しかも回避手順は「書いた本人は今それを必要としていない」
  ときに書かれる一方、読むのは**困ってから**の人なので、いちばん余裕の無い
  タイミングに誤りが配達される。repo に検査機構がある場合は**手順がそれと
  両立するか**まで見ること — 回避手順が検査を落とすなら、それは手順ではなく
  設計課題として書く。
  実例: issue #283 で `codex/config.toml` からマシン固有の `notify` を削除した際、
  「必要な人は merge 後に手元の `~/.codex/config.toml` へ手で追記する」と書いた。
  実際には (a) ファイル末尾に足すと TOML 仕様上 直前のテーブル配下のキーになり、
  トップレベル設定である `notify` としては解釈されない (パースエラーも出ないので
  黙って無効になる)、(b) 機能する唯一の置き場所であるトップレベル領域は
  `codex-merge-config.sh` が書く base の prefix 内部なので、置くと
  `tests/integrity/run-integrity-check.sh` の base 一致検査が落ちて `make gate` が
  毎ターン失敗し続ける。どちらも書く前に 1 回試していれば分かった
  (レビュアーが実測して覆し、こちらも `tomllib` で測り直して確認した)
- **原則をコメントに書き足したら、同じ diff の中でその原則を破っていないか
  grep する**。レビュー指摘に応じて原則を明文化した直後が、いちばん自分の
  違反に気付けない — 「いま書いたばかり」という記憶が確認の代わりになるため。
  特に**同じ PR の後半で足したコード**が危ない。
  実例: issue #230 の対応で `EVAL_QNB` を「手書き複製は元の集合に追随せず
  黙って drift する」という理由で導出形に直した**その 6 行下**に、
  `EVAL_WORD_BT` を `EVAL_WORD` の手書き複製として足していた。drift の
  向きは検出漏れ側 (fail-open) で、テストは経路の入出力しか見ないので
  検出されない — 直した当の欠陥をそのまま再生産していた
- **停止条件を書いたら「書いた時点で既に発火していないか」を確かめる**。
  「〜を観測したら方針を切り替える」型の trigger は、*将来*の話として
  書かれるので、**その観測が既に手元にあることを見落とす**。到達可能性
  (停止条件がそもそも満たされうるか) とは別の外し方で、こちらは
  「満たされているのに発火しない」形で出る。書いた直後に、いま持っている
  観測を trigger に当ててみること。
  実例: issue #230 で「経路追加では届かない FN を観測したら一般化に
  切り替える」と書いたが、その FN (Markdown の箇条書き接頭辞 2 文字で
  位置集合を外せる形) は**同じファイルの数十行上に「観測済み」と書いて
  あった**。trigger を書いた瞬間に発火済みで、それでも経路追加を続けていた
- **`mktemp -d` はテンプレートを明示する** (`mktemp -d "${TMPDIR:-/tmp}/<name>.XXXXXX"`)。
  macOS の BSD mktemp はテンプレート無しだと **TMPDIR を無視**して
  `confstr(_CS_DARWIN_USER_TEMP_DIR)` の per-user temp dir
  (`/var/folders/.../T`) を使うため、TMPDIR を差し替えた環境では作業先が
  意図とずれる。GNU coreutils は TMPDIR を見るので、**macOS でだけ**
  「TMPDIR を設定したのに効かない」形で出る。
  実例: issue #196 の対応中、sandbox 下で `TMPDIR` を書き込み可能な場所に
  差し替えて手元検証したところ `mkdtemp failed on /var/folders/...:
  Operation not permitted` で落ちた (スクリプト側のバグではなく mktemp の
  仕様差)。テンプレートを明示すると BSD / GNU どちらでも TMPDIR に従う
- **一時ディレクトリのパスを「外部ツールが返す値」と文字列比較するテストでは、
  `${TMPDIR:-/tmp}` を連結する前に末尾スラッシュを落とす**。macOS の TMPDIR は
  末尾がスラッシュ(`getconf DARWIN_USER_TEMP_DIR` → `/var/folders/.../T/`)
  なので、そのまま連結すると WORKDIR に `//` が入る。一方で比較の相手側は
  `//` を潰した値を返すことが多く(fish の `fish_add_path` は
  `builtin realpath -s`、`scripts/link.sh` は `cd` + `pwd`)、生パスとの比較
  だけが一致しなくなる。TMPDIR に末尾スラッシュが付く環境でのみ落ちるため
  **flaky に見えるが実際は決定的**で、原因に辿り着くのが高い。
  剥がした後も `//` が残る場合(`TMPDIR=/a//b`)は、一部ケースが無言で落ちる
  代わりに原因つきで即死させるガードを置く。
  適用条件は「**比較する**」場合に限る — 一時ディレクトリを作って使うだけで
  正規化前後のパスを突き合わせないテストは対象外(repo 内の `${TMPDIR:-/tmp}`
  利用約 18 箇所のうち、実測で末尾スラッシュ有無に結果が依存したのは下記
  3 箇所だけだった)。
  実例: issue #225 / `tests/fish-pnpm/`・`tests/fish-version-managers/`・
  `tests/link/`(前 2 者は fish の `$fish_user_paths` と、後者は `readlink` が
  返す symlink target と比較していた)
- **`${TMPDIR:-/tmp}` 配下に掘った作業ディレクトリを「`/tmp` 配下」の代用に
  しない**。前項が TMPDIR の*表記*(末尾スラッシュ)の話なのに対し、これは
  **TMPDIR がどこを指すか**の話。`mktemp -d "${TMPDIR:-/tmp}/…"` で掘った
  ディレクトリは、TMPDIR 未設定の環境でだけ /tmp 配下になる。macOS は
  per-user temp dir (`/var/folders/.../T`) を指すので、そこを「/tmp 配下」の
  代表として使う検査は**前提ごと崩れる**。
  外れ方が悪質なのは、**Linux では原理的に再現しない**こと — この前提により
  CI の Linux matrix は全 green のまま、macOS job だけが落ちる。手元の macOS
  でも、agent の harness が TMPDIR を /tmp 配下の scratchpad
  (`/tmp/claude-<uid>` 等) に差し替えていれば通る (2026-08-10 実測: 修正前の
  スイートが手元では 80/80 pass)。「/tmp 配下」を測りたいなら
  **/tmp 配下であることを自分で確かめた probe ディレクトリ**を別に掘る
  (`/tmp` 直下は 1777 なので、掘るのは 0700 のサブディレクトリ)。
  実例: issue #316。html-brief renderer の「TMPDIR が /tmp の外を指しても
  /tmp 配下への出力は受理される」ケースが出力先に `WORKDIR`
  (= `${TMPDIR:-/tmp}` 配下) を使っており、macOS runner では TMPDIR を
  差し替えた時点でどの root にも入らなくなっていた。**レンダラは正しく
  拒否しており、落ちていたのはテストだけ** (3 ロケールとも同一箇所)。
  退行が main に入ったのは 2026-08-02 〜 08-09 の間だが、macOS CI は週次
  実行なので **検出は 08-09 の定期実行まで遅れた** (main の実行履歴で
  failure はこの 1 本、直前の 08-02 は success。2026-08-10 実測)。
  「赤かった期間」ではなく **気付けない期間が最長 7 日ある**ことがコスト
- **テスト用の一時 git リポジトリを作ったら、`git init` の直後に
  `git config gc.auto 0` と `git config maintenance.auto false` を置く**。
  `git commit` は auto gc を detach して起動するため、これがテスト終了時の
  `trap` の `rm -rf` と競合し、`.git/objects/info/packs` と `.git/info/refs` を
  書き戻す。結果として **全ケースが pass していても `rm` が ENOTEMPTY で失敗し、
  スイートが exit 1 になる**。commit 数が増えるほど発生確率が上がり、症状が
  「たまに落ちる」なので flaky と誤診しやすい(実測: 無効化前は 20 回中 2 回、
  無効化後は 30 回連続 green)。
  現在 repo 内で一時 git リポジトリを作るのは
  `tests/classify-risk/run-classify-risk-tests.sh` と
  `tests/session-compact/run-session-compact-tests.sh` の 2 箇所。
- **シェル設定の検証は「そのファイルが読まれる起動モード」で行う**。設定ファイルを
  直したあと動作確認するとき、**起動モードを間違えると設定ファイルが一度も
  評価されず、検証コマンドが別物を測る**。しかも出力はもっともらしいので
  誤診に気付けない。この repo は zsh と fish の両方の設定を管理しているので、
  同型の取り違えは繰り返し起こりうる。**検証コマンドを書く前に「この設定
  ファイルはどの起動モードで読まれるか」を 1 回確認する**こと:
  - zsh の `.zshrc` は **対話シェルでしか読まれない**。`-l`(login)だけでは
    読まれないので、`zsh -lc '...'` は `.zshrc` の検証に**使えない**
    (`zsh -lic '...'` のように `-i` が要る)。`.zprofile` は login で読まれる
  - 非対話シェルは呼び出し元の環境を継承するだけなので、**出力は「呼び出した
    シェルの状態」**になる。fish から `zsh -lc` を叩けば fish の PATH が見える
  実例: issue #219 で `~/.zshrc` から `RBENV_ROOT` の上書きを削除した後、
  検証に `zsh -lc 'echo $RBENV_ROOT; rbenv root; which -a ruby'` を使った。
  `.zshrc` が読まれないため fish から継承した PATH が出て `/usr/bin/ruby` が
  先頭に見え、**移行は成功していたのに「system ruby にフォールバックしている」と
  誤診して user に報告した**。`-i` を足すと shims が `/usr/bin` より前
  (13 番目 vs 19 番目) にあり、`ruby -v` も 3.4.2 で正常だった
- **修復操作を勧める診断メッセージは、その操作が観測を破壊しないかを先に見る**。
  検知器が「〜してください」と次の行動を指示するとき、**その操作が原因究明の
  材料そのものを消すなら、誤診のコストは片側だけ回復不能**になる。通常の
  誤診は「無駄足を踏む」で済むが、こちらは**真因が二度と観測できなくなる**。
  したがって判別条件は「たいてい当たる」では足りず、外れたときに何が失われるかで
  厳しさを決める。**確信を持って判別できないなら、断定せずに判別材料を提示して
  user に選ばせる**(選択肢を並べる出力は冗長に見えるが、非対称なコストの前では
  それが正しい既定)。あわせて 2 点:
  - **判別条件は実測で確かめる**。「この症状ならこの原因」は直感で書けてしまう。
    原因側を実際に作る mutant を当てて、条件が本当に分離するかを見る
  - **分岐を書いたら「出さない側」も pin する**。「出るべきときに出る」だけを
    測ると、条件を `if true` に緩めた退行が全 pass で通り、**誤誘導が常時
    発火する**状態になる(受理パターンの広さを検査する項と同じ構図)
  実例: issue #214 で、`trusted_hash` 不一致の原因を件数で出し分け、
  「一部だけ不一致 = 承認後に hooks.json を書き換えた」として
  **「codex TUI で再承認してください」**と出していた。だが codex の payload
  仕様が変わった場合も、変わった規則に依存する entry しか外れない — 実測で
  `timeout` 既定値を変えた mutant は 8 entry 中 1 件しか外さず、仕様変更が
  「個別の書き換え」と診断された。**再承認すると codex が新しい hash を
  書き戻すので、仕様が変わったという唯一の証拠が消える**。加えて分岐条件
  `mismatch == ok + mismatch` は算術的に `ok == 0` と等価で、新しいマシン
  (承認済みが少ない状態) でも誤発火していた。
