# 成果物に書く主張の規約

docs・コメント・コミットメッセージに書く事実と手順の規約。
実例の `#N` は dotfiles の issue / PR。他 repo のものは `owner/repo#N` で書く。

- **コメントに書く「外部環境の事実」は、書く前に実測して測定日を添える**。
  runner イメージの pre-install 内容、ダウンロード先ドメイン、成果物サイズ、
  `bash` / `awk` の解決先、CLI オプションが実際に拾うエラー種別などは、
  もっともらしく書けてしまう上に**設計判断の根拠として引用される**ため、
  外れると判断ごと腐る。**根拠つきの断定**を書くときは、その根拠を必ず 1 回測る
  (`curl -sI` の Location、`ls -l` のバイト数、runner-images の README、`man` の該当項)。
  **ただし測定日を添えること自体は保証にならない** — 「(YYYY-MM-DD 実測)」と書く行は
  **その 1 行が対応するツール実行結果を指せるか**を書いた直後に確かめること。
  とくに**否定形の断定**(「〜は効かない」)を設計判断の根拠にするときは、**対照付きで**
  測ってから書く(「設定が読まれていない」でも同じ観測になるため)。
  この項は lint で機械検出しない(「実測」ラベルの真偽は字面から判定できない)。
  実例: issue #196 で 1 PR のうちに 4 件外した (redirect 先ドメイン、tarball サイズ、
  `bash <path>` 起動での shebang、`--retry-connrefused` の対象)。issue #289 (PR #292) で
  「(実測)」タグ付きの否定形の断定が 2 件とも対照付きで測ると逆だった
- **測る対象が repo 自身なら、その数値をコメントの根拠にしない**。コーパスが repo
  自身だと (a) その節を書き足す行為自体が数を動かし、(b) 走査方法の差 (`git grep` は
  symlink 配下が当たらない等) で別の値になる。書くなら走査方法と自己参照性を明記し、
  **同一時点で取った差分**を判断に使う。
  実例: issue #230 で同じ件数が 57 / 60 / 62 と毎回違った (差分の側は毎回再現した)
- **「こうすれば回避できる」と書いたら、その手順を一度は実際に通す**。回避手順の
  誤りは「手順どおりにやっても何も起きない」形で出て、読むのは困ってからの人になる。
  repo に検査機構がある場合は**手順がそれと両立するか**まで見る — 回避手順が検査を
  落とすなら、それは手順ではなく設計課題として書く。
  実例: issue #283 で「`~/.codex/config.toml` へ手で追記する」と書いたが、末尾に足すと
  TOML 上は直前のテーブル配下になり黙って無効、トップレベルに置くと integrity の
  base 一致検査が落ちて `make gate` が毎ターン失敗する形だった
- **原則や停止条件を書いたら、その場で手元に当てる**。原則は同じ diff を grep して
  自分が破っていないか、「〜を観測したら切り替える」型の停止条件はいま持っている
  観測で既に発火していないかを確かめる。書いた直後は「いま書いたばかり」の記憶が
  確認の代わりになる。
  実例: issue #230 で `EVAL_QNB` を drift 防止のため導出形に直した 6 行下に
  `EVAL_WORD_BT` を手書き複製として足していた。同じ issue で書いた trigger の FN は、
  同じファイルの数十行上に「観測済み」と書いてあった
- **1 サンプルで測った結果を一般化して書かない**。書く前に repo 内の既存の実測記述
  (DESIGN.md 等) を探し、矛盾しないか確かめる。
  実例: ymnao/scaena#71 で 1 本だけ build して「外部通信しない」と書いたが、反例
  (絵文字・数式・テーマの外部参照) が DESIGN.md に実測として書かれていた
- **防御・伏せ込みを足したと書く前に、同じ入力が通る他の分岐を数える**。数えられない
  なら、主張を効く分岐の側に狭めて書く。
  実例: ymnao/scaena#58 で URL の認証情報を 4 分岐のうち 1 つでしか伏せていないのに
  「伏せる」と書いた
- **閾値 (timeout / 上限) で守る形は、実測した通常コストと桁が離れているか見る**。
  同じ桁なら、その閾値が切るのは固まった run ではなく遅かった正常な run になる。
  実例: ymnao/scaena#68 で待ち上限 20 秒に対し通常の実測が 19.9 秒だった
- **「N ケース回した」と「N ケース一致した」は別の数**。一致しなかったケースを先に
  数え、その扱いを同じ文に添える。
  実例: ymnao/scaena#75 で 9 ケース流して一致は 8 だった
- **要約・言い換えは新しい主張**。言い換えた先の文を根拠 (`git show`・ツール出力の
  文言・diff の件数) に当て直す。当て直せないなら引用の形のまま残す。
  実例: ymnao/scaena#76 で警告「2 deprecated subdependencies found」を「2 行入る」と
  書いたが、自分の diff が足したのは 1 行だった
