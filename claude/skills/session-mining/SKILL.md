# session-mining

AGENTS.md の「同じ指摘を 2 回受けたら追記を提案する」を、セッションをまたいでログから拾い直す。

出す候補は 2 系統で、混ぜずに分けて出す:

| 系統 | 拾うもの | 候補の形 |
|---|---|---|
| 訂正 | 否定・ダメ出し・やり直しの指示 (「そうじゃない」「勝手に〜した」「また〜」) | してはいけないことを止める規則 |
| 既定化 | セッションをまたいで毎回付けている指示・前置き・条件 | 言わなくても実行される既定 |

## Steps

### 1. 抽出

引数をそのまま渡す。期間の指定が無ければ直近 30 日になる。
`<scratchpad>` はシステムプロンプトにあるこのセッションの scratchpad の絶対パスを
リテラルで書く。

```
python3 -I ~/.claude/skills/session-mining/scripts/extract.py --out-dir "<scratchpad>/session-mining" <引数>
```

出力の会計表 (除外理由ごとの件数) は報告にそのまま載せる。何件を見て何件を落としたかが
無いと、後から網羅性を確かめられない。

project 別の件数に、実験用の clone・scratchpad・`agent-sdk-spike` などが混ざっていたら、
その発話は user が普段の作業で打ったものではない。`--exclude-project <部分一致>` を足して
抽出し直し、外したことを報告に書く。

user が agent を中断した位置と tool を拒否した位置は、`[user が中断した。直前の tool: …]`
の形の印として発話の列に入る。理由はたいてい次の発話にある。

ログには貼り付けた資料や秘密情報が含まれうる。出力は scratchpad の外に書かず、
Artifact・issue・PR に引用しない。

### 2. fan-out の規模を確かめる

チャンク数 × 2 系統がサブエージェントの数になる。8 を超えるなら起動の前に user に伝え、
期間を狭めるか、そのまま回すかを決めてもらう。

### 3. チャンクを読ませる

1 体に 1 チャンク・1 系統を渡す。同じチャンクに両方の系統を頼まない (片方に偏り、もう片方が薄くなる)。
Agent tool で `subagent_type: "general-purpose"`、`model: "sonnet"` を指定する。
互いに独立なので 1 回の応答で並列に起動する。

依頼文に入れるもの:

- 対象ファイルの絶対パスと、**全文を読むこと** (Read を分割して最後まで)
- その系統で拾うもの・拾わないもの
  - 訂正: 拾うのは agent の振る舞いへの否定・やり直しと、中断・拒否の印の直後の発話。単発の作業依頼・仕様の説明・承認 (`ok` 等) は拾わない
  - 既定化: 拾うのは別々の日・セッションで繰り返される指示や条件。その回限りの作業内容は拾わない
- 返す形 (1 候補ごと): 症状の一般形 / 出現した `===== ` 見出しの日時・project・セッション id の一覧 /
  原文の引用 (日付付き、ログの文面そのまま) / 何が起きたか / 規則の案
- **最大 10 件**。該当が少なければ少ないまま返す。推測で埋めず、引用はファイルにある文面から取る

### 4. 件数を一次データで確かめる

サブエージェントの件数はそのまま採らない。同じ文面の連投や、同じセッション内での言い直しを
別件として数えるため。各候補について `turns.jsonl` を grep し、**別セッション数**に直す。
2 セッション以上で起きたものだけを候補に残す (1 セッション内の繰り返しはそのセッションで対処できた)。
step 1 の「2 セッション以上で同じ文面の発話」の一覧は、既定化の候補の取りこぼしを見る基準に使う。

### 5. 既存の規則と突き合わせる

候補ごとに、次の置き場を Grep して下の表のどれかに分ける:

- `~/.claude/CLAUDE.md` (dotfiles の `agents/AGENTS.md`)、`~/.claude/rules/`、`~/.claude/skills/*/SKILL.md`
- 発話があった repo の `CLAUDE.md` と `.claude/rules/`
- memory (`~/.claude/projects/<project>/memory/`)

| 分類 | 意味 | 打ち手 |
|---|---|---|
| 不在 | どこにも書かれていない | 追記 |
| 事後検知 | 書かれているが、失敗してから気付く形になっている | 手順を事前の確認に変える |
| 過剰適用 | 規則が広すぎて、当てはめたくない場面にも出ている | 除外の条件を足す |
| 対応済み | 既に書かれている | `git log -S` で書かれた日を出し、その日より後に再発があるかを見る |

対応済みでも、規則が入った後にまた起きているなら書き足しでは止まっていない。
機械で判定できるなら hook、できないなら skill の手順の中の確認に格上げする候補にする。

### 6. 提示して止める

候補ごとに次の 4 点を揃えて出す。揃わないものは出さない:

1. 実測値 (別セッション数・期間、step 4 の grep)
2. 分類 (step 5) と、対応済みなら規則の入った日
3. 置き場: 全 repo に共通する振る舞いは `agents/AGENTS.md` か `claude/rules/`、
   repo 固有はその repo の `CLAUDE.md`、特定の手順の中だけなら該当 skill、
   機械で判定できて再発しているなら hook、その repo の事実・経緯なら memory
4. 規則の文面の案 (判定基準と手順。日付・引用・固有名詞は根拠の欄に置き、文面に入れない)

最後に、確かめていない範囲を書く: 打ち切った長い発話、除外した project、
サブエージェントが読んだのは user の発話と中断・拒否の印だけで、agent 側の発言を見ていないこと。

採否を user に聞いて止める。**このスキルではファイルを書き換えない**。採用されたものは
別に `/dev <自由文>` や issue に渡す。
